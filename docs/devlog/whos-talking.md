# Who's talking

Branch `whos-talking`. Alexa+ recognizes voices, so the simulated Echo Show now asks who's speaking, and the sample household's rules change with the person: a kid's plans wait for a parent, a parent approves them from a screen, private events stay private, the farm hand sees the ranch, and a guest can look but not change anything.

## 2026-10-17

### What I built

- **Roles as data** (`src/sample/roles.ts`, on the sample's state). Each role says which calendars it sees, whose chores and whereabouts, whether it changes anything at all, which changes wait for an approver (every time, or only when they're for someone else), and whether it approves. People hold roles by name ("Parent", "Kid", "Farm hand"), and two roles belong to no one: "Guest" for a voice Alexa doesn't recognize and "Shared screen" for a call that names nobody. The code reads the fields; nothing branches on a person's name. A test flips `approves` on the Kid role and the approvers change with no code touched.
- **The rules in the sample household** (`src/sample/index.ts`). Every call runs as an actor. Private events are in full only for their `owner` (Sam's gift shopping), Busy for everyone else, and a search finds them only for the owner. The farm hand sees the Ranch calendar, their own chores and ones up for grabs, and only where they are; their events go on the Ranch calendar right away. A guest reads the calendar, chores and lists, hears nothing about whereabouts, and every change is refused, check-offs included. A kid's event, a task for someone else, a list item and a skip come back `waiting_for_approval` with `approvers` (whoever's role approves: Sam and Alex) and a `requestId`; check-offs, taking a chore, undoing and counting supplies never wait.
- **Approvals.** `approvals` answers `{ toDecide, yoursWaiting, requests? }` and `decide_approval` takes `{ request, decision: "approve" | "decline" }`. Approving runs the change as it was asked, as whoever asked, so the sleepover lands on the calendar; declining a list item takes it back off the list. The ice cream already on the grocery list is now a real request from Leo, so a parent has something waiting from the start.
- **The approvals screen** (`widgets/approvals`, `show_approvals`, on `widgets/shared/screen.ts` and the `screen()` helper). A card per request with who asked, what, and when, a big Approve and a Decline; decided cards stay in view marked Approved or Declined; a kid sees their own requests "waiting for Sam or Alex"; an empty state says nothing's waiting. Taps go through `decide_approval`, so only someone who approves can, and the assistant hears what was tapped.
- **The simulator** (`echo/`). A "Who's speaking" picker built from the household's own `people` tool plus "Someone Alexa doesn't recognize". The device greets the person by name for a moment ("Hi, Maya") and keeps a quiet name pill at the top. Every MCP call carries the speaker in `x-demo-person`, the traffic log says "as Maya" on each call, and the screen that's up redraws as the new speaker would see it. Each thing said tells Claude who Alexa recognized, so a switch mid-conversation is clear. Two suggestions are said by someone: "Maya: Can I have a sleepover at Ava's on Friday?" and "Sam: Anything waiting for me?" switch to that person first.
- **Server and docs.** The header is read only in sample mode (`src/index.ts`); corral mode never sees it. The approval tools and screen are listed only for a household that decides requests. The skill, tool reference and README cover speakers and approvals.
- **Tests.** `test/speakers.test.ts` (29: who's who, private events, the farm hand, guests, every kind of change that can wait for every person, approvals end to end) and `test/speaker-header.test.ts` (8: the header in sample mode, the whole beat over MCP, switching speakers mid-connection through `requestInit`, and corral mode ignoring the header and listing no approval tools). `pnpm check` passes with 100 tests.

### Decisions, and why

- **The simulator starts as Sam**, the household's first member (the picker takes the first person the `people` tool lists, so it isn't hard-coded). In real life the person who sets up the Echo and links the account is usually a parent, and starting as a parent means every existing suggestion works on a judge's first click. Starting as a guest would refuse the first "Leo emptied the dishwasher", and starting as Maya would turn half the suggestions into requests before anyone knows why.
- **No header is the shared kitchen screen, exactly as before.** Alexa+ itself, the MCP Inspector and the preview page send no speaker, so the sample behaves for them as it always did (and the earlier tests pass unchanged). Only the simulator names a speaker.
- **A name nobody here has is a guest, not an error.** Failing closed means a typo or a stale name never gets more than a guest may. A 400 would have broken the MCP client mid-conversation for no benefit.
- **The header is URI-encoded**, since an HTTP header can't carry every name as it's written.
- **"Decline", not "Deny".** The brief said Approve and Deny buttons; Corral's own app and its assistant both say Approve and Decline, and the decision values are `approve` and `decline`. The screen, the tool and the spoken summaries all say Decline so a family sees one word everywhere.
- **The answers keep Corral's shapes.** `approvals` keeps the shape of Corral's own inbox (`toDecide` with `id`, `from`, `asks`, `since`; `yoursWaiting` with `decidedBy`), and `decide_approval` takes Corral's `request` and `decision`. Approving runs the held change, as Corral's requests do.
- **Linked mode doesn't list the approval tools.** Corral's MCP server deliberately offers no way to decide requests to any credential, so forwarding `approvals` would only ever fail. `Household.decidesRequests` turns them on; the sample says yes, `CorralHousehold` doesn't.
- **What waits for a kid.** An event always (it changes plans for the family), a task only when it's for someone else or up for grabs (a reminder for themselves happens now), a list item always (it goes on the list marked "waiting for a parent", like the seeded ice cream), and a skip always (it takes a chore off everyone's list). That follows Corral's split between changing the plans, which can wait, and doing what's planned, which never does.
- **A guest hears nothing about where people are.** "Read the day" covers the calendar, chores and lists. Telling an unrecognized voice that the kids are at school felt wrong for a family product, and it makes the Today screen visibly different for a guest.
- **Credit for a check-off** goes to whoever's named, else the one person it's for, else whoever's speaking. "I collected the eggs" from Maya credits Maya; Sam tapping Leo's dishwasher chore still credits Leo.
- **The speaker goes to Claude in the conversation, not the MCP instructions.** The page reads the server's instructions once, at connect; a speaker named there would go stale on the first switch. A line like "(Alexa recognized the voice: Maya Rivera, Kid.)" before each turn keeps every turn attributable in the history.
- **Switching keeps the conversation**, as a shared Echo would; the per-turn line says who's talking now.

### Friction log

1. **Testing taps inside an MCP Apps screen.** The browser automation refused clicks inside the screen: "the press ... could not be attributed to a frame (frame owner is CSS-transformed (scaled))". Every host that scales a 1280 by 800 Echo Show frame to fit a window will hit this. Workaround for the test: inject a style that removes the scale for a moment, click the real button, put the scale back. There's no headless harness for an `App` either, so the widget's own button code can only be exercised in a real browser.
2. **Changing a header mid-connection in the MCP client SDK.** `StreamableHTTPClientTransport` takes `requestInit` once, at construction. Changing the speaker without reconnecting works only because 2.3.1 builds each request's headers from `requestInit.headers` afresh (`_commonHeaders`), which isn't documented. Reconnecting instead would orphan every `AppBridge` holding the old `Client`. A test now guards the behavior so an SDK upgrade can't silently pin the first speaker.
3. **No standard for "who's speaking" on a shared device.** MCP identity is the bearer token, which is one account per connection. A kitchen Echo is used by a whole family; voice ID knows who's talking, but neither MCP nor the Alexa+ docs available describe passing a recognized person per request. Feature request: a per-request speaker claim (signed, in `_meta` or a header) for multi-user devices, or guidance that each recognized person links separately.
4. **Server instructions are per connection.** Anything that depends on the speaker can't go there, so it moved into the conversation.
5. **Parallel tool calls have no order.** In one turn Claude called `add_list_item` and `show_approvals` together; the screen could have been drawn before the change landed. It happened to work. The skill now says to show a screen in the step after a change.
6. **A log race in the simulator.** The traffic log read "who made this call" after the response came back, so tools Claude ran together were labeled by whoever finished last (the model's `show_approvals` showed as the screen's). It now captures who when the call goes out.
7. **Class names in single-file screens collide easily.** The decided card's `approve` modifier picked up the Approve button's colors and turned "Maya asked" dark on dark. That's the second collision in this repo (the last commit before this branch fixed a `screen` class blanking the device). Scoped selectors from here on.
8. **TypeScript and the `screen()` helper.** The helper wants a `Record<string, unknown>`; an `interface` isn't assignable to that (no index signature) while the same shape as a `type` is. The approvals answer is a `type` for that reason alone.
9. **`echo/` wasn't typechecked.** Vite strips types without checking, and no tsconfig included the simulator. It's in `tsconfig.screens.json` now, and it passed.
10. **A blank screen that wasn't a bug.** Screenshots right after a screen mounted showed an empty device for a second or two while the frame painted in the background pane. Worth knowing before chasing it.
11. **Shell quoting.** A Python heredoc through the shell tool collapsed an escaped quote inside a TypeScript string; edits with nested quotes went through files instead.
