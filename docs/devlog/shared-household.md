# Devlog: one shared household on two Echo Shows

Branch `shared-household`. Notes kept while building, newest last.

## 2026-10-17: what was there

In sample mode, `src/index.ts` kept a `SampleHousehold` in module memory. Every Worker isolate had its own, so two devices (or two requests landing on different isolates) could see different households, and a restart lost everything. The judges list "maintains state across sessions" as creative, and two Echo Shows agreeing on screen is easy to see on video.

## 2026-10-17: what I built

- **A Durable Object per sample household** (`src/sample/durable.ts`, `SampleHouseholdObject`). In sample mode `/mcp` goes to the object for the household (`demo` unless `?household=` names another), which serves MCP from inside itself with `createMcpHandler`, exactly as the Worker did. The household is kept in the object's own SQLite database and survives restarts and deploys.
- **The household logic outside the object** (`src/sample/shared.ts`, `SharedSample`): load or seed, start over when the household's day changes, start over on request, keep the household after every call that changed it, and a change counter. Storage is behind a two-method interface (`src/sample/store.ts`): `sqlStore` for the object, `memoryStore` for tests and for a config without the binding.
- **Routes** (`src/sample/routes.ts`): `/mcp` through the object; `GET /household` (name, day, change counter); `POST /household/reset` (after the demo passcode when the server has one).
- **Screens that catch up**: `household_version`, a tool only screens can call (MCP Apps `visibility: ["app"]`), returns the counter. `widgets/shared/screen.ts` asks it every 3 seconds while the screen is on screen and refreshes when it moves.
- **Two devices in the simulator** (`/echo?devices=2`, `echo/pair/`): a kitchen Echo Show 8 and a barn Echo Show 5 side by side, each the simulator's own page in a frame, so each is its own MCP client with its own conversation and screen. The header shows the counter and pulses when it moves; "Start the day over" resets the household and both conversations.
- **Wrangler**: the binding and the class declaration for the top level (local dev) and `env.demo`; production explicitly has neither.

## 2026-10-17: decisions and why

- **One object per household, named.** `getByName(id)` with `demo` as the default keeps "one demo household" while leaving room for more: `?household=take-2` on `/echo` or `/mcp` gives a separate household (for a recording take, or a judge who wants a private copy). Ids are checked (`[a-z0-9-]`, up to 40) before an object is woken, so a typo can't make arbitrary objects.
- **MCP through the object's `fetch()`, the rest over RPC.** The Durable Objects guidance prefers RPC methods, but MCP over Streamable HTTP is request in, response out, so forwarding the `Request` with `stub.fetch(request)` is the honest fit and keeps headers, method and streaming intact. `status()` and `reset()` are RPC methods.
- **One JSON row, not tables.** The sample is a small document (about 10 KB) that's always read whole, so it's one row (`day`, `version`, `state`) in a table the object makes in its constructor. The SQL API is synchronous, so a change and its save happen before any other request reaches the object; no `blockConcurrencyWhile` needed. Temporal values (whereabouts use `Temporal.Instant`) are tagged in the JSON so they come back as themselves.
- **Keep whatever changed, not a list of write tools.** After every tool call the household is serialized and compared with what's kept; if it differs, it's saved and the counter goes up. A list of "write tools" would silently miss any tool another branch adds to the sample (the ranch branch is adding some). Serializing 10 KB per call costs microseconds.
- **The counter never goes back.** It keeps counting through resets and new days, so a screen can't mistake a fresh household for the one it saw.
- **A kept household from another build starts over.** If a deploy adds a part to the sample (say the ranch branch's devices), a kept household without it would crash the new code, so on load a kept household missing any top-level part a fresh seed has is started over. Same day rule as before: its times are laid out around today, so a new day starts it over.
- **Without the binding, one household per isolate, as before.** Unit tests that build an `Env` by hand (and any old config) still work. With the binding, sample mode always goes through the object; corral mode never looks at it.
- **Polling a counter, not shortening every refresh.** Options I weighed:
  - Server notifications or resource subscriptions: not available on a stateless Streamable HTTP endpoint, and Alexa+ connects statelessly.
  - Shorter refresh while two devices are up: the screen can't know that, and it would re-fetch the whole view every few seconds on every screen.
  - The host re-sending tool results: works only in our simulator, not on a real Echo Show.
  - A change counter the screens poll: tiny answers, works in any MCP Apps host (including real Echo Shows, if Alexa+ proxies app-only tool calls as the spec says), and a screen only re-fetches its view when something changed. Chosen, at 3 seconds while the screen is visible, with the existing minute refresh kept as a backstop.
  - A linked Corral has no counter: the tool isn't listed, the screen's first ask fails, and it stops asking (after transient failures it drops to once a minute instead of stopping).
  - The simulator keeps these polls out of its traffic log unless one fails, so the log still reads as a story; the refresh they trigger does show.
  - Known extra: the device that made the change refreshes once more when its next poll sees its own change. Harmless (about 10 ms), and removing it would open a window where another device's change could be missed.
- **`exports`, not `migrations`.** Cloudflare's docs (updated September 2026) say new Workers should declare Durable Object classes with the declarative `exports` field; `migrations` is "legacy". Neither demo nor production has a class yet, so this is the moment to start on `exports`. It can't be mixed with `migrations` and can't go back once deployed.
- **Production is told "none" twice.** `durable_objects` bindings aren't inherited by environments, but `exports` is, so `env.production` sets `"durable_objects": { "bindings": [] }` and `"exports": {}`. A test reads Wrangler's own resolved config for each environment (`unstable_readConfig`) and checks it.
- **Reset needs the passcode when there is one.** Everyone on the public demo shares one household; the passcode that guards the model also guards wiping it.
- **Two devices as frames of the existing page.** Each device being the real `/echo` page (with `?embed=1&place=Barn&show=5`) means two genuinely separate MCP clients and conversations, almost no change to the simulator's logic, and fewer conflicts with the branch adding speaker identity to the same page. The frame page passes "new conversation", "home" and "ask for the passcode" by `postMessage`; a passcode saved on one device reaches the other and the frame page through the `storage` event.
- **Sizes.** The grid gives the kitchen 1.38 parts to the barn's 1: an Echo Show 8's screen is about 6.8 inches wide and an Echo Show 5's about 4.9. Each device fits both the width and the height it's given. In a tall column (side by side at 1280 by 800) each device shows three suggestions and its MCP traffic under its talk bar; stacked on a phone or tablet it's the screen and the talk bar.
- **The model hears which room it's in.** `/echo/model` takes `context.place` and adds "This display is in the barn." to the second system block (the cached first block didn't change apart from one word: "home" instead of "kitchen").

## 2026-10-17: verified

- Tests with a fake namespace of real `SampleHouseholdObject`s on Node's own SQLite (`node:sqlite`): sample mode reaches the object; two MCP clients see one change and the counter moves; the household survives dropping every object (a restart) and the row is there; a new day starts it over; `?household=` keeps households apart; bad ids never wake an object; status and reset with and without the passcode; corral mode never asks the namespace for anything (a namespace that throws if touched); a linked household offers no counter; Wrangler's resolved config per environment.
- `wrangler dev --port 8803` (real workerd, local Durable Object): two MCP clients from Node, one checks off "Collect eggs", the other sees the counter move and the chore done; stopped and restarted the server and the chore was still done; reset with and without a passcode (`--var DEMO_PASSCODE:...`).
- In the browser at `/echo?devices=2`: a tap on the kitchen screen checked off "Collect eggs" and the barn screen showed it 3 seconds later (its log shows the refresh); typed "Leo emptied the dishwasher." on the barn device with the real model (Claude through the Claude API, from `.dev.vars`), which checked it off and answered, and the kitchen screen caught up; "Start the day over" reset both screens and conversations; with a passcode set, the kitchen device asked for it, both cards cleared when it was saved there, and the reset went through.
- Layout screenshots in headless Edge at 1280 by 800, 1920 by 1080, 768 by 1024 and 390 by 760, plus the single-device page unchanged at 1280 by 800.
- `wrangler deploy --dry-run` for `demo` (binds `SAMPLE_HOUSEHOLDS`) and `production` (no Durable Object).

## Friction log

- **Wrangler, `exports` versus `migrations`.** The docs now say to prefer `exports`, but most examples, quick references and agent skills (including the Durable Objects skill I loaded) still show `migrations`. The docs don't say whether an environment's `exports` replaces or merges with the top level's; Wrangler's source shows it replaces (`inheritable`). I only trusted it after reading Wrangler's resolved config.
- **Wrangler, inheritance is asymmetric.** `durable_objects` bindings aren't inherited, `exports` and `migrations` are. So an environment that should have no Durable Object needs both emptied, and even with an explicit `"bindings": []` Wrangler still warns that `SAMPLE_HOUSEHOLDS` "exists at the top level, but not on env.production". There's no way to say "none on purpose", and the warning sits beside the existing ones about `vars` and `ratelimits` that production also leaves out deliberately.
- **Wrangler, lifecycle changes need a full deploy.** `wrangler versions upload` and gradual deployments refuse a version that creates a class. Fine, but worth knowing before the first `pnpm ship:demo`.
- **Wrangler on Windows.** Stopping the background `wrangler dev` (ending its shell) left Wrangler's Node process and two `workerd` processes holding the port. I had to find them by command line and path and kill them.
- **Wrangler, pleasant surprise.** `wrangler dev` noticed it was running under an agent and printed its Local Explorer API (Durable Object namespaces, traces) up front.
- **Testing a Durable Object without the Workers runtime.** This repo's tests run in Node. Cloudflare's Vitest integration is the documented route, but moving the suite was out of scope, so the object runs on a stand-in `DurableObjectState` whose `storage.sql` is Node's `node:sqlite` behind the same `exec(...).toArray()` shape. Real SQL, fast, and the real runtime (under `wrangler dev`) behaved the same. Node 22 prints an ExperimentalWarning for `node:sqlite` on every run, and `cloudflare:workers` needed a `DurableObject` class in the test stub.
- **The MCP SDK inside a Durable Object.** No friction: `createMcpHandler(...).fetch(request)` runs unchanged inside the object's `fetch()`; nothing in SDK v2 assumes a Worker's top level.
- **MCP and MCP Apps, no change signal.** A stateless server has no way to tell a screen "your data changed": notifications and resource subscriptions need a session, and MCP Apps has no server-to-screen hint. Every app with shared state will reinvent a poll. A standard "change token" in a tool result's `_meta` that hosts could watch (or poll for the app) would help.
- **A missing tool's error shape.** Whether calling a tool the server doesn't have comes back as an `isError` result or a JSON-RPC error (-32602) depends on SDK version and era, so the screen handles both.
- **Browser automation.** The in-app browser refused to click inside the simulator's screen ("frame owner is CSS-transformed (scaled)"), and the sandboxed MCP Apps frame (no `allow-same-origin`, by design) is out of reach of page scripts. To verify a real tap I unscaled the screen for a moment and moved it into view. Emulated 1280 by 800 screenshots in a smaller pane came out mis-scaled, so layout checks used headless Edge through Playwright.
- **Tooling.** A Python heredoc edit through the Bash tool lost a backslash (`\\n` became a newline) and failed its own check; the Edit tool was the fix.
