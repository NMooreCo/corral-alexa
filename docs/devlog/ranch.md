# Devlog: ranch automation

Notes from building the ranch half of Corral for Alexa+: generic devices, the real greenhouse connector, the forecast, animal collars, the Ranch screen, the freeze routine and the morning briefing. Written as it happened, for the submission's friction log.

## 2026-10-17

### What got built

- **Tools:** `devices` (read), `set_device` (switch on or off, or run for N seconds or minutes), `weather`, `trackers`, and two MCP Apps screens, `show_ranch` and `show_briefing`, plus a screen-only `refresh_ranch`. All live in `src/ranch/`; the sample's specifics are data in `src/sample/ranch.ts`.
- **The greenhouse connector** (`src/ranch/greenhouse.ts`) speaks the ESP32 valve controller's firmware v0.1 API (`GET /status`, `POST /on?sec=N`, `POST /off`, `X-Api-Key`) and maps it to the generic device shape: the valve with its run timer and cap, the air sensor (temperature, humidity, station pressure, age, ok), and five soil probes.
- **Local only, real hardware:** `pnpm dev:lan` plus `GREENHOUSE_URL` and `GREENHOUSE_KEY` in `.dev.vars` swaps the simulated controller for the real one. `pnpm greenhouse:fake` is a stand-in controller for trying it without the hardware.
- **Sample ranch:** a fenced, L-shaped property with seven zones, a simulated greenhouse controller, eight simulated animal-care devices (greenhouse heater, two stock tank heaters, a waterer, a coop heat lamp, a barn heater, a propane tank, a garden drip line) and six simulated collars.
- **Skill:** ranch ground rules, a freeze recipe and a good-morning recipe in `skills/corral-household`.
- **Tests:** 62 new (geometry with randomized property checks, the connector against a fake controller, each device's limits, the forecast against stubbed Open-Meteo, collars, both screens over MCP, the practice model).

### Decisions, and why

1. **Limits are data, never a code path per device.** A device carries `maxRunS`, `defaultRunS`, `presetsS` and `failsafe`. `set_device` reads only those: a device with a cap always runs for a set time (its default when none is said), a longer run is refused with the limit stated so the assistant can offer it. `kind` exists only so a screen can pick an icon.
2. **The sample greenhouse runs through the real connector.** Rather than a separate fake for the sample, `simulatedController()` answers the firmware's own routes and JSON in-process, so the demo exercises exactly the code that talks to hardware, and the tests use the same simulation as their fake controller (plus hand-made ones for failures).
3. **The live connector can't leak into a deploy.** It needs three things at once: `GREENHOUSE_LAN=true` (only `pnpm dev:lan` sets it, as a CLI var), both `GREENHOUSE_URL` and `GREENHOUSE_KEY` (only ever in the git-ignored `.dev.vars`), and a request whose own host is loopback or a private LAN address. A deployed Worker fails the last check even if someone set the others.
4. **`dev:lan` drops `global_fetch_strictly_public` with a CLI flag, not a new Wrangler environment.** `wrangler dev --compatibility-flags nodejs_compat` replaces the config's flags for that run only. A `lan` environment in `wrangler.jsonc` would have been one `wrangler deploy --env lan` away from existing in the cloud; a CLI flag has nothing to deploy. `wrangler.jsonc` only gained a comment.
5. **A tighter cap than the firmware's.** The firmware caps a run at 1800 s; the household config caps the misters at 600 s (and `GREENHOUSE_MAX_RUN_S` can set the live cap, never past 1800). A misheard "thirty minutes" stays a ten-minute mistake.
6. **Real soil probes read raw millivolts.** The controller's design doc is explicit that a percentage needs dry and wet points measured in each bed, and that bench references would mislead. So the live beds read "1,850 mV" with a note that higher is drier, and only the simulated beds (with made-up calibration) read percentages. The firmware's bench-test fault ranges (4 to 10 mV wiring, 200 to 400 mV no probe) become reading faults.
7. **How a device fails is said out loud.** A valve's safe failure is off and a heater's is on; that's `failsafe` in the data, it comes back from `devices` as `ifUnreachable`, the skill tells the assistant to say it when a device isn't answering, and the Ranch screen asks for a second tap before switching off a device whose safe state is on.
8. **`set_device` shows the Ranch screen.** It's registered as an MCP Apps tool linked to the Ranch resource: the change goes to the model as text, the whole ranch view goes to the screen as `structuredContent`. So "run the misters for 30 seconds" by voice puts the countdown in front of whoever asked, with no polling. The bridge's own `/preview` lists only screen tools that need no arguments, so it skips `set_device`.
9. **The model hears a summary, the screen gets the drawing.** `show_ranch`'s view holds SVG paths the model doesn't need, so the `screen()` helper in `src/server.ts` gained an optional `say` that turns a view into what the model reads (who's outside the fence, what's running, what needs attention).
10. **Propane is a device reading, not a Corral supply.** A propane tank's level comes from a sensor in real life, and keeping it out of the sample household's seed avoids touching a file other branches are changing. The freeze routine reads both `devices` (propane) and `supplies` (feed).
11. **The map is drawn, not tiled.** A flat local projection (meters east and north) is accurate to well under a meter at ranch scale, so the server projects the fence, zones and collars into SVG coordinates and the screen draws them. No map tiles, no other origins, and the screens keep declaring empty CSP domains.
12. **Night is 6 PM to 7 AM for the sample's runaways**, so an evening demo (the freeze routine is an evening request) shows Scout and Pepper outside the fence.
13. **The freeze routine asks once.** Reads go out together in one turn; then one question covers every device and the task for whoever is home; low propane or feed is a second, separate offer, as the skill's "don't chain changes without a yes" rule requires.
14. **Screens wait at most 2.5 s for a cold forecast**, then go up without it; the fetch still fills the ten-minute cache for the next refresh.
15. **No ranch tools in linked mode yet.** A real Corral doesn't serve ranch configuration over MCP today; the natural next step is a Corral pack that carries the property map, devices and connectors, at which point the same tools register for linked households.
16. **A small simulator fix.** The traffic log tagged only the first of several side-by-side tool calls as the assistant's (the rest came out as "screen"), which undersold exactly the multi-tool turns this feature is about. The page now sets the caller around the whole batch.

### Verified

- `pnpm check` passes: build, both typechecks, 124 tests.
- **The misters beat, against a fake controller:** `pnpm dev:lan` with `GREENHOUSE_URL=http://127.0.0.1:8899` and `GREENHOUSE_KEY=fake-key` in `.dev.vars`, `pnpm greenhouse:fake` running, and the real model. "Alexa, run the greenhouse misters for 30 seconds." The assistant read `devices`, asked "Should I run the greenhouse misters for 30 seconds?", and on "Yes." called `set_device {"device":"greenhouse.valve1","state":"on","seconds":30}`; the fake controller logged `POST /on?sec=30` with the key, the simulator mounted the Ranch screen, and the run counted down. The fake closed the valve at 30 s and the screen asked for the real state as its countdown reached zero. Also checked against this machine's own LAN address: `dev:lan` reached it in 0.1 s.
- **The freeze routine, real model, sample greenhouse:** "It's going down to 12 tonight. Get the place ready." One turn called `weather`, `devices`, `trackers`, `whereabouts` and `supplies` together. It said the forecast was 48 but planned for 12, that the greenhouse heater was on, that the tank heaters, coop lamp and barn heater were off and Scout and Pepper were outside the fence, and asked once. On "Yes, do it." it made four `set_device` calls and an `add_task` for Sam (home; Jon was off the ranch) naming where each animal was, then offered propane (18 percent) and dog food for the feed store list, and added both on "yes".
- **Good morning, real model:** `show_briefing`, then a two-line summary (two animals outside the fence, four late chores, dog food low).
- **Taps and card changes:** the simulator's screen frame is sandboxed, so taps were checked in a same-origin test host: a tank heater turns on from its tile and the assistant is told; a heater's "Turn off" asks for a second tap; a misters preset starts a countdown; a `set_device` result sent to an open Ranch screen shows the countdown; on the briefing, a dot tap and a swipe each tell the assistant which card is showing, and touch hosts get no buttons.
- **Sizes:** the Ranch and briefing screens at Echo Show 8 (1280 by 800), Echo Show 5 (960 by 480) and phone width, light and dark.

### Not verified

- The real controller. Everything up to the HTTP call is the same code path the fake exercised, and the request shape matches the firmware's routes, but I had no access to the hardware.
- A real Alexa+ (the toolkit is partner-only).

### Friction

- **Wrangler, `global_fetch_strictly_public` in local dev.** A fetch from the Worker to a LAN address didn't fail and didn't honor `AbortSignal.timeout(4000)`: it hung until the caller gave up (over 40 s with curl). A fetch to `127.0.0.1` went through. Nothing in the output pointed at the flag, so it looked like the controller was down. An immediate error naming the flag would have saved the detour.
- **Wrangler on Windows, stopping `wrangler dev`.** Killing the `wrangler dev` process left its `workerd.exe` children running and holding the port. The next `wrangler dev --port 8802` printed "Ready" while the old instance kept answering on that port with the old variables, which made a config change look like it had no effect. Fixed by finding and stopping the `workerd` processes by command line.
- **Wrangler and the OAuth provider disagree under `dev:lan`.** Without `global_fetch_strictly_public`, `workers-oauth-provider` warns that Client ID Metadata Documents are disabled and recommends adding the flag back. Harmless in sample mode, but the warning reads like a misconfiguration.
- **MCP Apps, seeing a screen.** A host must sandbox the screen's frame, so neither a browser automation tool nor the host page can script or even screenshot inside it (the frame captured as black). Checking the screens' layout and taps needed a separate same-origin test host and headless Edge screenshots, and headless Edge's `--screenshot` exited 0 without writing a file about half the time; retries with a fresh profile and its output piped made it dependable.
- **MCP Apps, `content` versus `structuredContent`.** The MCP spec says a tool that returns structured content should also return it as text for backward compatibility. For a map that's kilobytes of SVG paths the model shouldn't read, so `show_ranch` sends a summary as text instead. It's unclear whether Alexa+ shows `structuredContent` to the model, which decides whether that's a waste or a necessity.
- **MCP Apps, actions that update a screen.** There's no way to say "this tool is an action that shows this screen" as distinct from "this tool opens this screen". Hosts and previews that list screen tools and call them with no arguments will call `set_device` with none and get an error; the preview filters on required arguments.
- **MCP Apps, model context from a carousel.** `ui/update-model-context` replaces what the screen said before, which is right for "the card showing now", but a swipe through seven cards would send seven updates. The briefing waits until a card has been showing for 0.9 s.
- **Open-Meteo.** Free, no key, and fast to adopt; passing `elevation` matters for a place well above its grid cell's average height, which reads warmer. Rough edges: cold requests reported `generationtime_ms` of 700 to 1,300 ms, so a first forecast took about 2 s end to end; times come back local with no offset (they only make sense with the `timezone` parameter); there's no "tonight's low", so it's computed from hourly temperatures across midnight; the miles-per-hour unit string is `mp/h`; and a day's maximum gust can come back lower than its maximum wind (both are printed as given).
- **Halo collars.** No public API that I could find, so collars are simulated behind a generic feed shape a real one can fill.
