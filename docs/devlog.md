# Dev log

What we did, in order, with what went wrong and what we decided. Product friction that the hackathon asks about is written up properly in [feedback.md](feedback.md) (F1 and on); this log points to it. Each feature built in its own branch keeps its own notes in [devlog/](devlog/), folded in here when it merges.

## Friday, October 16, 2026

- **Picked the track.** Read the hackathon pages and chose Alexa+: put Corral, our family's household platform, inside Alexa+ through MCP rather than replacing Corral's own assistant. Corral already had an MCP server for Claude and Home Assistant, so the question was what Alexa+ needs on top.
- **Found the tooling is partner-only.** The MCP Toolkit's setup page reads as self-serve, but the CLI, Local Inspector and web simulator are for select partners, with no way to apply ([F1](feedback.md#f1-finding-out-the-add-on-tools-are-partner-only), [F5](feedback.md#f5-local-inspector-described-but-not-available)). We decided to build to the published contract and make a faithful simulator.
- **Split out this repository.** Corral's repository is private and much bigger than the judges need, so corral-alexa is its own MIT project: it reaches Corral only through Corral's OAuth and `/mcp` tools, and carries a made-up sample household (Juniper Hollow) so it runs with no account.
- **MCP server and the Today screen.** Started on the v1 MCP SDK; MCP Apps 2.x needs the v2 SDK's types, which we only learned from mismatched types ([F7](feedback.md#f7-mcp-apps-2x-needs-the-v2-mcp-sdk)). Moved to `@modelcontextprotocol/server` 2.3.1, whose `createMcpHandler` serves both protocol eras (2025-11-25 for Alexa+, 2026-07-28 for current clients) from one stateless endpoint.
- **Account linking.** Built on Cloudflare's `workers-oauth-provider`. Two gaps against Alexa's contract: Alexa reads protected resource metadata only at the root, where the library answers 404 ([F2](feedback.md#f2-protected-resource-metadata-at-the-root-only)), and Alexa wants a bare 401 ([F3](feedback.md#f3-no-www-authenticate-on-a-401)). We serve the root document ourselves and strip the header. Smaller snags: the library rejects a user id containing a colon, and Vitest can't load `cloudflare:workers` until it's aliased to a stub.
- **Linked to our real Corral.** With a stand-in for Alexa, went through Corral's own consent page: sign-in, code exchange, tool calls with the person's token (134 to 204 ms each, the Today screen 396 ms) and refresh (602 ms, token rotated).
- **Deployed** two Workers on custom domains: the linked bridge and the open demo. `pnpm deploy` turned out to be pnpm's own command, so the scripts are `ship` and `ship:demo`. Measured from home, the deployed bridge answered tool calls in 123 to 354 ms, inside Alexa's 500 ms budget.

## Saturday, October 17, 2026

- **Read the FAQ again:** no entrant can reach a real Alexa+; a web page acting as a real MCP client is the accepted demo, and showing another assistant on the same server is a bonus.
- **Built out** the Today screen on the MCP Apps patterns (a screen-only refresh tool, polling that pauses offscreen, full screen, host fonts, telling the model what was tapped), three more screens (Week, List, Supplies), the `corral-household` Agent Skill (also served as an MCP prompt), and the simulated Echo Show at `/echo`: a real MCP client with a live traffic log, voice in and out, and the screens on the device.
- **Tried Claude on Amazon Bedrock** for the simulator. A brand new AWS account, even after moving to the Paid plan, had every Claude model's quota at 0; Opus 5.5 first said it wasn't available for the account, and Haiku needed a use-case form ([F8](feedback.md#f8-a-new-bedrock-account-has-no-claude-quota)). We asked for the quota; the form won't take less than the default ([F9](feedback.md#f9-the-quota-form-and-what-it-covers)). The requests are pending.
- **Made the model provider a setting.** The same Anthropic SDK call runs against Bedrock's Messages endpoint or the Claude API (`MODEL_PROVIDER`), so the demo runs on the Claude API now and can move to Bedrock with one setting. The page names whichever answers.
- **Tested the whole demo script with the real model.** Every request did the right thing: the Today screen for "what's going on today", a chore checked off with credit to the right child, a supply count recorded then added to the feed store list after a yes, an event confirmed first and then sent to the parents to approve, a correct "not yet" for the eggs. About two seconds per model turn, with the prompt cache warm after the first turn.
- **Bugs we found in our own simulator, and fixed:**
  - The demo passcode box appeared below the suggestions, off the bottom of the screen, so the passcode got typed into the question box and the visitor was asked again and again. It's now a card over the device, focused when the page opens, says when a code is wrong, and re-asks the waiting question.
  - The Corral screen vanished about a minute in. The traffic log tagged rows with a class named for who made the call, so the screen's own refresh made a tag with the class `screen`, which took the device screen's styles and covered it. Log rows now use a data attribute.
  - The sample household's whereabouts were a hand-written weekday schedule, so on a Saturday the Today screen showed Maya at soccer practice while "Where's Maya?" said home. Whereabouts now follow the calendar (private events never say where).
- **Testing screens with browser automation was hard.** MCP Apps screens run in sandboxed frames that automation can't click or read, and screenshots of them sometimes came back blank ([F10](feedback.md#f10-testing-sandboxed-mcp-apps-screens)). We tested taps through the bridge in unit tests and the bridge's debug messages instead.
- **Planned the build-out from the judging criteria.** The rules call a basic MCP wrapper obvious, and name agentic workflows across services, state across sessions, cards and carousels, MCP Apps and Agent Skills as creative. Four tracks started in parallel, each in its own branch:
  - **Who's talking:** pick who's speaking (as Alexa+ voice profiles do), so a child's request waits for a parent and parents approve it on a screen.
  - **Ranch automation:** a real greenhouse (our misters run from an ESP32 controller, so the video can show them turn on by voice), real weather, animal waterers and heaters, ten animal GPS collars on a property map, a "freeze tonight" routine across all of them, and a morning briefing carousel.
  - **One household on two devices:** the sample household in a Durable Object, shown on a kitchen and a barn Echo Show that update each other.
  - **Upstream fix:** a contribution to `workers-oauth-provider` for the account-linking gaps above.
- **The upstream contribution, narrowed after review.** Two independent reviews and our own checks against the sources cut it to one opt-in option, `serveResourceMetadataAtRoot`, for the root document (F2). We dropped the header option: Alexa starts linking from the 401 or 403 status, and nothing showed the header breaks it, so it wasn't worth asking a library to break an HTTP requirement. The reviews also caught our own overstatements: a diagram that put Alexa's discovery at the wrong moment (the CLI reads the document when account linking is configured, not after each 401), and a "no client is worse off" claim the MCP SDK's behavior didn't support. One thing we can't check ourselves: Amazon's tooling is partner-only, and its pages disagree (the guide's example has the document at the root naming `/mcp`; the quickstart uses a bare-origin URL). So the issue and pull request wait until we've asked Amazon at office hours on Monday, October 19.
- **The three features, merged.** Each was built on its own branch, with its own log: [who's talking](devlog/whos-talking.md), [one household on two devices](devlog/shared-household.md) and [the ranch](devlog/ranch.md). Merging them took real integration, not just conflict fixes:
  - The household moved into a Durable Object, so who's speaking had to reach inside it. The shared household now gives each request a view as its speaker, and still saves the household and moves its change counter after every call.
  - The ranch lives beside the household in the same object, in memory, so a misters run started from the kitchen counts down on the barn's screen too.
  - Who may switch the ranch's devices became part of each role, as data: parents, the farm hand and the shared screen may; a kid or a guest is told who can.
- **Tested together with the real model.** Maya asked for a sleepover and it waited; Sam saw it on the approvals screen and approved it by voice, and it landed on the calendar. Leo asking for the coop lamp was told a grown-up has to. "It's going down to 12 tonight" called the forecast, devices, collars, whereabouts and supplies in one turn, switched four devices after one yes, gave Sam a task to bring in two animals outside the fence, and offered propane and dog food for the list. A second, separate client saw the same devices on. Two small things turned up and were fixed: a run's time left could read "11 hours 60 minutes", and in the two-device view the speaker pickers pushed the talk bar off the screen. 190 tests pass.
- **Made the demo video.** We recorded the autoplay run with the real model in headless Edge, then laid voices over it: Cartesia voices for a narrator, each person and Alexa, with Alexa saying her actual answers word for word. Only the model's thinking time is sped up, and the video labels it. Along the way:
  - The recording starts about a third of a second after the page's clock, so the captions led our event log until we shifted for it.
  - At three minutes the cut had to lose Sam's "Anything waiting for me?" and the last "Yes, add both."
  - One honest moment stayed in: asked to get ready for 12 degrees, the model said the forecast only shows 48 and planned for 12 anyway.
  - The real misters and the Claude connector clip still need filming at home.
